**2026-07-28 限时抢购联调翻车血泪(用户暴怒),用户点破的根因+六条症状规则,以后死守:**

## 🎯 最深根因(用户原话):搬运/换皮也要先过策划案流程,别一上来直接搬——"搬的一坨屎"
搬运/换皮/新功能,**动手前先过一遍策划案流程**(X3见[[workflow_x3_festival_design_doc]]),别跳过直接"把X2的prefab/配置搬过来"。策划案流程逼你在动手前把功能拆清楚(所有模块×界面元素×交互×验收点)——**下一条那张「全量验收checklist」就是策划案流程的产出物**。跳过它直接搬=没图纸砌墙:搬来的X2一坨(横屏prefab/占位数据555·9999/X2脚本残留LC_/item组件占位/DK混registry)全成坑,后面一个个踩到用户崩溃。**判据**:接到"搬X2的XX到X3"这种活,别立刻开搬,先出/对齐策划案(哪怕是搬运也要一份"搬什么+改什么+验什么"的spec),再动手。

## 🎯 根因(用户原话):做功能开工没设计「全量验收checklist」→ 后面全是即兴
所有症状都是这一个根长出来的。**做任何功能,开工第一步=先设计一张全量验收checklist**:把这功能"做完"拆成可勾选的原子项——界面每个元素(每个按钮/文本/图标/状态态)× 每个功能(每条协议/每个交互)× 每张配置 × 每个验证点(每项怎么验通),逐条列死、给用户过目。**然后:照它执行(不即兴发挥,超出的先问)、照它逐条验(不随缘抽查)、照它报进度(状态=打勾数,不靠"感觉快好了")。** 没这张表 → 乱做+随意发挥+随缘检查+瞎说,越做越崩(实证:限时抢购没列全量checklist,界面bug一个个冒、验收一轮轮翻车、用户崩溃)。checklist设计四原则见 [[workflow_checklist_design_principles]]。

## 六条症状规则(都是"没checklist"的具体表现,一并守):

1. **状态只报实的,禁画饼。** 别说"可演""马上好""就差临门一脚"——除非真验死了。每次报状态给一张「真做完(可查证)/真没解」两栏账,不挑好听的说。用户宁可听"还有5个bug"也不要听"马上好"然后又冒一个。**根因毛病=优先让用户"感觉快好了"而不是"知道真实情况",这最伤协作。**

2. **问题一次列全,禁挤牙膏。** 界面/功能有多个bug时,**一开始就彻底诊断、把完整清单一次给用户**(按根因分类),别图标→555→IAP→价格一个个往外冒逼用户一轮轮"还是不行"。用户不该靠发火问"你还有什么没改好的"才拿到全清单。

3. **架构判断先证伪再下结论。** 别拿假设当事实说(如"IAP本地测不了"被用户点破"周卡/开箱明明能测")。下"做不了/没有"这种断言前,先找一个反例验一验。

4. **验证到死再报,别信自述。** agent自述+半吊子grep不算验证("钩子加了"其实位置错/"价格显示了"其实是预告期)。报"好了"前现场跑通/日志见证。

5. **快速移动的共享分支:一验就推,别死循环。** 见 [[workflow_x3_merge_conflict_audit]] ⚡段。dev_festival多人高频推,"合→验→改→再验"会永远追不上。

6. **战线拖长主动喊停。** 本地联调链路lossy(Unity不reimport/bytes被git还原/多人WIP混着)每步都磨时,早点主动说"核心已成,剩的是明确尾巴,集中一次收拾"给用户选,别陪着在实时里逐个bug磨到用户崩溃。判据:同一功能反复"还是不行"≥3轮 → 停下改策略(批量修+一次验),别继续零敲。
