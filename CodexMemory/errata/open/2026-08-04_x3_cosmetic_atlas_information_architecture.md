# X3 节日外显养成线页面先做模块定位与内部分层

- 日期：2026-08-04
- 任务：X3 节日外显模块养成线梳理 HTML
- 现象：首版以“10 个模块总览 + 每模块双北极星”为主体，用户指出应当每个模块独立页签，并优先讲清养成线定位及其内部细分，例如英雄皮肤的普通/史诗/限定、装饰的普通/史诗/限定、主城的传说/限定。
- 根因：把“列全模块与指标”误当成信息架构，没有先建立每条养成线的产品层级；模块级指标过早，掩盖了不同品质层实际承担的投放任务差异。
- 处理：HTML 改为一模块一页签，页内固定按“定位 → 子类型/品质层 → 投放职责 → 当前情况 → 双北极星”展开；用户已确认的分层明确标记，尚未确认的模块只给候选框架并标待核实。后续指标需要能下钻到具体子层，不只停留在模块总量。
- 二次纠错：页签版虽然补了目标定位与候选分层，但“当前情况”仍只是一条投放演进，没有清楚展示当前实际定位、已有数据表现和数字所暴露的问题。结构再次调整为“当前盘面（实际定位 + 数据卡 + 核心问题）→ 目标定位 → 内部分层 → 投放演进 → 双北极星”；历史基线、近期实绩和数据缺口必须显式分层。
- 三次纠错：英雄皮肤页只用了白皮书的整体饱和度与付费率，没有先查知识库中已经存在的“英雄皮肤分层 × 获取率”专项报告。专项口径是 `皮肤曾获得人数 / 对应英雄解锁人数`，成熟服 1000–1880、数仓实查 2026-07-29，共48款可获取皮肤；应优先于全体MAU饱和度用于判断皮肤本身的获取表现。后续查 X3 英雄皮肤数据，先查 `C:\ADHD_agent\KB\产出-数值设计\X3_8-10月节日需求\英雄皮肤分层与获取率.html` 及生成链 `skills\p2-festival-monitor\x3_skin_ownership.py`。
- 四次纠错：补了分层定义和汇总仍不够；用户要的是“每个分类具体有哪些皮肤”。模块分层交付必须列资产名单，至少包含具体名称、获取人数、目标分母与获取率；其他历史标签也要单列，不能藏在汇总或默认归入普通。
- 五次纠错：具体皮肤名单还必须逐款带上“所有已确认投放方式”，不能只列皮肤名和获取率；同一皮肤有礼包、常驻、排行或活动多路时要并列展示，来源未定位的明确写“待补”，禁止凭经验补全。
- 附带工具错误：首次按 `errata\open\README.md` 读取模板失败；实际模板位于 `errata\README.md`，已改用正确路径。
- 附带工具错误：AGENTS 文本中的 `.Codex\projects\...` 知识库路径在本机不存在，真实共享 KB 位于 `.claude\projects\...`；后续先 `Test-Path` 再读。另一次 PowerShell `Get-ChildItem -Filter` 误传字符串数组，改为分别读取或用 `Where-Object`。
- 附带工具错误：用 `node - <path>` 从 stdin 做语法检查时误取 `process.argv[1]`（实际为 `-`），目标路径应取 `process.argv[2]`。另外初步口头估计“3款来源待补”，全量录完核对实际为4款（兔耳魅影、游艇假日、金海商使、黑金契约），最终以页面红标与校验数为准。
