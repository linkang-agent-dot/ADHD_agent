# X2 搬来的按钮换成 X3 标准件 —— 操作说明书

> 场景：X2→X3 搬运的界面，功能跑通了但按钮还是 X2 美术。
> 本文以**马戏节限时抢购（FlashSale）九格货架的三个购买钮**为实例，流程通用。
> 编制：2026-08-04，路径与节点名均已对真 prefab 解析确认（非猜测）。

---

## 0. 先明确：换的是"皮"，不是"骨"

| | 换件影响 |
|---|---|
| 购买逻辑 / 三态切换 / 限购 / 记账 | ❌ 完全不受影响（都在代码里，已实机验证通过）|
| 按钮**外观** | ✅ 这才是要换的 |
| `Auto_` 里的**绑定路径** | ⚠️ 会变（新件的子节点名不同）—— 换完必须改 + 重跑断言 |

**换件前的功能状态必须是"已验证通过"**，否则换完出问题分不清是换件引入的还是原本就有的。

## 1. X3 标准按钮件库

位置：`client/Assets/Res/UI/Prefab/Common/Button/`

| 件 | 内部子节点 | 适用 |
|---|---|---|
| `button_Payment` | `txt_price` · `txt_get` | **IAP 内购钮**（真金价格 + "获得"）|
| `button_PaymentClaim` | — | 内购已购 / 待领取态 |
| `ButtonYellowBig` | **`Text` · `icon_text`**（实测直接子节点只这两个）| 软货币 / 通用钮（`icon_text`=货币数值，`Text`=纯文案）|
| `Button_Gray` | **`icon_text` · `Text`**（实测直接子节点只这两个）| 置灰 / 不可点态 |
| `ButtonOrangeBig` / `ButtonOrangeMid` / `ButtonGreenMid` / `ButtonBlueBig` / `ButtonBlueMid` / `ButtonRedMid` / `ButtonGoldSmall` / `ButtonSmall` … | 未逐个实测 | 其它色系/尺寸，用前**先跑工具「①预演」看真实子节点名** |

> 🔴 **子节点名一定要用工具「①预演」打出来的，别用 `grep m_Name`**。
> 我最初就是 grep 得到 `icon`/`text`/`Text`/`icon_text` 四个名字并写进本表 —— 那是
> **文件里任何位置**（含嵌套件内部、非激活节点）的名字集合，**证不了谁是直接子节点**。
> 实测 `ButtonYellowBig` 只有 `Text`+`icon_text`、`Button_Gray` 只有 `icon_text`+`Text`，
> 小写 `text` 和 `icon` **根本不是直接子节点**。同一个坑本案栽过三次（`Btn/RedPointTips`、`Card/Icon`、这次）。
| `Common_Btn_3_green` / `Button3` / `Button4` | — | 其它通用样式 |

> ⚠️ **X2 Migration 菜单里没有"按钮替换"工具**。`Tools ▸ X2 Migration` 只有 5 项：
> `AllianceFlag → UIAllianceSymbolUnit` / `CommonItemShow → UIItemTemplate` / `Head1 → UIPlayerAvatar`
> / 多语言键回填 / 清理 RTL missing 组件。**按钮只能手换。**

## 2. 本例的对应关系（限时抢购三个购买钮）

| 现有（X2） | 换成 | 绑定路径变化 |
|---|---|---|
| `BoxNormal/BtnBuy`（IAP 直购）| `button_Payment` | ✅ **不用改** —— 子节点名 `txt_price`/`txt_get` 与现绑定完全一致 |
| `BoxNormal/Price`（钻石档）| `ButtonYellowBig` | ⚠️ `Price/Layout/txt` → `Price/icon_text` |
| `BoxNormal/BtnBuyCd`（不可购/售罄）| `Button_Gray` | ⚠️ `BtnBuyCd/Layout/txt` → **`BtnBuyCd/Text`**（大写 T）|

**为什么 `BtnBuy` 不用改**：X2 那个内购钮的子节点命名恰好和 X3 `button_Payment` 一致（都是
`txt_price`/`txt_get`），大概率是同源。这属于运气，**别假设其它界面也这样**，一律按第 4 步实测。

## 3. Unity 里怎么换（逐步）

以 `Item1/BoxNormal/Price` 换成 `ButtonYellowBig` 为例：

1. **先备份**：`git status` 确认 prefab 当前状态干净或已提交；`FlashSale.prefab` 若未跟踪，先手动复制一份到别处。
2. Project 窗口定位 `Assets/Res/UI/Prefab/Common/Button/ButtonYellowBig.prefab`。
3. 打开 `FlashSale.prefab`（**Prefab 编辑模式**，不要在场景里改实例）。
4. Hierarchy 里选中 `Content/Grid/Item1/BoxNormal/Price`，**记下它的 RectTransform 数值**
   （anchoredPosition / sizeDelta / anchorMin / anchorMax / pivot / scale）—— 换件后要抄回去，
   否则位置会跳。
5. 把 `ButtonYellowBig` 拖进 `BoxNormal` 下，成为 `Price` 的兄弟节点。
6. 把新件的 RectTransform 按第 4 步的数值填回。
7. **把新件重命名为 `Price`**（原 `Price` 先改名 `Price_old`）——
   🔑 **保持节点名不变是关键**：这样 `Auto_` 里 `BoxNormal/Price` 这一层路径不用动，
   只有内部子节点路径要改（见第 2 步表格）。
8. 确认新件显示正常后，**删除 `Price_old`**。
9. 保存 prefab。

**其余两个钮同法。** `BtnBuy` → `button_Payment` 时同样重命名为 `BtnBuy`。

## 6. 九格 = 27 处，怎么办

`FlashSale.prefab` 的 `Content/Grid/Item1..Item9` 是**复制出来的静态节点**
（实测 `FlashSale.prefab` 引用 `FlashSaleItem.prefab` **0 次**），所以没有"改一处传九格"。

| 方案 | 做法 | 成本 | 风险 |
|---|---|---|---|
| **① 复制 BoxNormal（推荐）** | Item1 换好三个钮 → 复制整个 `Item1/BoxNormal` → 替换其余 8 格的 `BoxNormal` | 8 次复制粘贴 | 低。九格节点集实测完全一致（`BoxNormal`/`BoxSoldOut`/`BoxClose`/`Limit`/`Remain`），复制不会丢差异 |
| ② 做成模板 prefab | 把货架格抽成独立 prefab，Grid 下放 9 个实例 | 中，且**代码要改**：从「包装静态节点」改成「克隆模板」（`UIWidgetList.Add(go)` → 模板克隆）| 中。结构更干净、以后改一处传九格，但动了已验证通过的代码路径 |
| ③ 不换 | 保持 X2 美术 | 0 | 只影响观感 |

**推荐 ①**：一次性成本最低、完全不动代码结构。
方案 ② 值得做的时机是"以后还要频繁改格子结构"，现在为了换皮去动它不划算。

⚠️ 方案 ① 复制后**仍要跑第 5 步的路径断言**，而且要
`--rel-base Content/Grid/Item5`、`Item9` 各抽验一次（确认九格一致，别只验 Item1）。

## 9. 🔴 尺寸：**绝不能把旧件的 sizeDelta 原样搬到新件**（2026-08-04 实测翻车）

实测数据（限时抢购九格购买钮）：

| | sizeDelta | scale | 视觉尺寸 | 长宽比 |
|---|---|---|---|---|
| **X2 旧钮** | 506.7 × 227.1 | **0.6** | 304 × 136 | 2.24 : 1 |
| `ButtonYellowBig` 原生 | 472 × **136** | 1 | — | **3.47 : 1** |
| `Button_Gray` 原生 | 420 × **134** | 1 | — | 3.13 : 1 |
| `button_Payment` 原生 | 684 × 254 | 1 | — | 2.69 : 1 |

把旧 `sizeDelta` 搬过去 ⇒ 新件高度被从 ~135 **强拉到 227（纵向 1.67 倍）** ⇒ 9 宫格切图拉花，
界面上就是一块"胖板"。**位置是对的，纯粹是尺寸策略错。**

✅ 正确策略（工具已内置为默认「保新件原生比例」开关）：
```
保 anchoredPosition / anchor / pivot（位置不变）
新件保持自己的原生 sizeDelta（不动）
localScale = 旧视觉宽 / 新件原生宽    ⇒ 横向占位不变、不变形
  ButtonYellowBig: 304/472 = 0.644 → 视觉 304 × 87.6
  Button_Gray:     304/420 = 0.724 → 视觉 304 × 97.0
```
高度会按新件比例走（通常比旧的矮）—— 这是**正确结果**，两者长宽比不同只能选对齐宽或对齐高，
货架格宽度固定所以对齐宽。⚠️ 旧件常带 `scale != 1`（本例 0.6），算"旧视觉宽"**必须乘上 scale**，
只看 sizeDelta 会算错 1.67 倍。

## 10. X3 标准钮的真实结构是**两层**，货币价签有专门写法

```
ButtonYellowBig / Button_Gray / ButtonBlueBig …
├ Text                  有 TFWText —— 纯文案槽
└ icon_text             **只是容器，自身没有 TFWText**
  ├ icon                货币图标（TFWImage）
  └ text                有 TFWText —— 数值
```
- ⚠️ 我一度把价格绑到 `Price/icon_text`（按名字猜它是文本）⇒ 运行时 `GetComponent<TFWText>` 返 null，
  而节点确实存在、Console 干净，典型"静默空白"。**靠运行时打日志才抓出来。**
- ⚠️ `grep m_Name` 会把两层的名字（`icon`/`text`/`Text`/`icon_text`）混成一层列出，**证不了层级**。
  用工具「①预演」打印的直接子节点，或 `tools/prefab_tree.py`。

**货币价签的权威写法**（参照 `UIPayGachaMain.cs:376`，同款嵌套件结构）：
```csharp
UIHelper.GetComponent<TFWText>(btnGo, "Text").text = string.Empty;      // 纯文案槽清空
var iconText = UIHelper.GetChild(btnGo, "icon_text");
iconText.SetActive(true);
var icon = UIHelper.GetComponent<TFWImage>(iconText, "icon");
UIHelper.SetImageWithDisplayKey(icon, CItem.I(costItemId).DKIcon);      // 🔑 图标走道具 DKIcon
UIHelper.GetComponent<TFWText>(iconText, "text").text = cost.ToString();
```
**X3 钻石 = 道具 1002**（服务端扣费 `UseRes 1002` 实证）。别依赖件自带的那个通用货币图。

## 13. 工具的三个尺寸模式 + 无头入口（2026-08-04 迭代到位）

`目标视觉宽度` 字段的约定（`RunHeadless` 的第二个参数同义）：

| 值 | 行为 | 什么时候用 |
|---|---|---|
| **-1** | **原生尺寸，`scale=1`** | **要把尺寸交给人工手调时用这个** —— 见下条 |
| **0** | 沿用旧钮视觉宽（旧 `sizeDelta.x × scale.x`），按宽等比缩放 | 想让新钮占位和旧钮一致 |
| **>0** | 绝对目标宽度，按宽等比缩放 | 自己定死一个宽度反复微调 |

### 🔑 为什么必须提供「绝对值」而不是只有「沿用旧钮」
**"沿用旧钮"在重跑时会累积** —— 第二次跑时"旧钮"已经是上一次换好的 X3 件，
再按它算就一次比一次小。绝对值（含 -1 原生）则**跑几次结果都一样**，才敢反复迭代。
> 通用规律：**任何"从当前状态推导目标"的批量工具都不可重复执行**。
> 要么做成绝对值/幂等，要么每次从干净底子（`git checkout`）重跑。本工具两条都支持。

### 🔑 交给人工调尺寸时，留 `scale=1` + 原生 `sizeDelta`
别留 `scale=0.644` 这种零碎缩放值给人拖 rect —— Inspector 里改 Width/Height 会和 scale 叠乘，很别扭。
`-1` 模式就是为这个场景做的。

### 🛠️ 无头入口（不用人点 UI）
```bash
python <repo>/.claude/skills/DebugUtils/scripts/client.py invoke   --type "Migration.X2ButtonReplaceTool" --member "RunHeadless" --kind call   --args "Assets/Res/UI/Prefab/Activity/FlashSale.prefab" -1
```
返回值就是完整报告（同时也 `Debug.Log` 进 Editor.log）。
> 规律：**自写的 EditorWindow 工具都该配一个 `public static` 无头入口**，
> 否则每次都要人去点，AI 侧没法自动化。加一个方法的成本换掉整条人工环节。

## 14. ⚠️ 边界：尺寸「看起来对不对」最终只能人眼定，工具只提供旋钮

## 15. 新增：`RunHeadlessDeleteOnly` —— 只删节点、不做替换（2026-08-04）

### 为什么要单独一个入口
换件做完后还想清死 UI，**千万别为了删节点去重跑 `RunHeadless`** ——
那会把已经是 X3 件的钮再替换一轮（第 13 节讲的"不可重复执行"就是这个雷）。

```bash
python <repo>/.claude/skills/DebugUtils/scripts/client.py invoke   --type "Migration.X2ButtonReplaceTool" --member "RunHeadlessDeleteOnly" --kind call   --args "Assets/Res/UI/Prefab/Activity/FlashSale.prefab"          'Content/Grid/Item*/BoxSoldOut
Content/Grid/Item*/BoxClose
Content/Grid/Item*/BoxNormal/ContBubble
Content/Grid/Item*/BoxNormal/Card/Icon'
```
它把所有替换规则 `Enabled=false`，只走删除分支。每行一个路径，相对界面根。

### 同时修掉的一个限制：废弃节点清单现在支持通配
原来删除走的是 `root.transform.Find(name)`，**只能删界面根下的整块**，
删不了"九个格子里各自那一份"。已改为走 `ResolveGlob`（纯名字仍照旧生效），
所以 `Content/Grid/Item*/BoxSoldOut` 这类逐格死件能一次清掉。
> 限时抢购实测：4 条规则 × 9 格 = **一次删 36 个节点**，替换 0 处。

### ⚠️ 跑之前两件事（都吃过亏）
1. **确认用户没在 Unity 里开着这个 prefab**（Prefab 模式 + 未存盘 ⇒ 会弹
   `Prefab Has Been Changed on Disk`，Keep/Discard 两个选项都会静默丢一边的改动，没有合并选项）。
   详见 `X3客户端GUI知识.md` 同名章节。
2. **先 `cp` 一份到 scratchpad**。prefab 常带未提交改动，git 兜不住。

### 删完必做的复核
不要只信工具报的数字，回头解一遍真 prefab YAML：
- 该没的：`grep` 死节点名，应为 **0**
- 该在的：三个购买钮各 **9** 个、`ItemMid` / `Card` 各 9 个
  （⚠️ `ItemMid` 全 prefab 会多出几个——限时抢购是 `Pop` 说明弹层里还有 4 个，
   **先确认多出来的在哪再下结论**，别看到数字不对就以为删错了。我这次差点误判）

## 16. 新增：`RunHeadlessSingle` —— 只换一个钮（换错模板时补救）

选错模板很常见（见 `X3客户端GUI知识.md` 的「公共目录混装」判据）。补救**别重跑 `RunHeadless`**
——那会把已经换对的钮再替换一轮。

```bash
python <repo>/.claude/skills/DebugUtils/scripts/client.py invoke   --type "Migration.X2ButtonReplaceTool" --member "RunHeadlessSingle" --kind call   --args "Assets/Res/UI/Prefab/Activity/FlashSale.prefab"          "Content/Grid/Item*/BoxNormal" "BtnBuyCd" "ButtonYellowBig" -1
```
参数：prefab / 父路径glob / 节点名 / 模板名 / 宽度（-1 原生，同第 13 节约定）。
它会 `mRules.Clear()` 只留这一条，并把 `mDeleteDead` 关掉（单钮补救不该顺手删东西）。

### 限时抢购最终落法（可直接抄的范例）
三个状态钮**全用 `ButtonYellowBig`**、全 472×136，"不可用"靠 `UIHelper.SetGray(go, true)` 出：

| 节点 | 内容落法 |
|---|---|
| `Price`（钻石） | `icon_text/{icon=货币图, text=数量}`，`Text` 隐 |
| `BtnBuy`（IAP） | `Text` = 现金价，`icon_text` 隐 |
| `BtnBuyCd`（即将开卖/售罄） | `Text` = 文案，`icon_text` 隐，**恒置灰** |

⚠️ 换完模板**必须**同步改 `Auto_` 里该钮的子节点路径 + 重新编译。
不同模板内部结构不同：`button_Payment` 是 `txt_price`/`txt_get`，
`ButtonYellowBig` 是 `Text` + `icon_text/{icon,text}`。

### 一条省时间的经验
**先问"这界面上已经确认对的钮用的是哪个件"，照它抄。**
本案我查命名风格 / 引用数 / sprite 路径绕了好几轮，
而正确答案就是"和旁边那个钮同款"。有正确样例时别做血统考古。

## 17. 五个无头入口总表（选错入口会白做，先看这张表）

`Migration.X2ButtonReplaceTool`，全部经 DebugUtils 桥 `invoke --kind call` 调用。

| 入口 | 干什么 | 什么时候用 | 会不会动位置 |
|---|---|---|---|
| `RunHeadless(prefab, 宽)` | 按默认规则表**全量换件** + 删死节点 | 第一次换皮 | 会（重新实例化） |
| `RunHeadlessDeleteOnly(prefab, 路径清单)` | **只删节点**（支持 `*` 通配） | 换完件再清死 UI | 不会 |
| `RunHeadlessSingle(prefab, glob, 节点, 模板, 宽)` | **只换一个钮** | 某个钮模板挑错了 | 会（重新实例化） |
| `RunHeadlessResize(prefab, glob, 节点, 宽)` | **只改 sizeDelta**，等比 | 只想改矩形大小 | 不会 |
| `RunHeadlessSetButtonScale(prefab, glob, 节点表, 缩放, 复位rect)` | **批量设 `ButtonScale.normal`** | **要「整体等比变小」就用这个** | 不会 |

### 🔴 选入口的两条铁律
1. **换件类入口会冲掉人工调过的位置/锚点** ⇒ 只想改大小时，用 `RunHeadlessResize` 或
   `RunHeadlessSetButtonScale`，**别用换件入口**。
2. **想「整体等比变小（含字号）」只能走 `RunHeadlessSetButtonScale`。**
   改 Transform.Scale 会被 `ButtonScale.OnEnable` 覆盖；改 Width/Height 只缩矩形不缩字。
   原理见 `X3客户端GUI知识.md` 的 ★ButtonScale 三连坑。

### 通用姿势
- **先只对一个格子试**（`Content/Grid/Item1/BoxNormal`），确认字段名/效果对了再换成 `Item*` 铺开
- 跑之前 `cp` 一份 prefab 到 scratchpad（prefab 常带未提交改动，git 兜不住）
- 跑之前确认对方**没开着 Prefab 模式**（否则弹 Keep/Discard，两边都会丢改动）
- 跑完**回头解 YAML 复核**，别只信工具报的数字。例：
  `grep -A1 "propertyPath: normal.x" <prefab> | grep "value:" | sort | uniq -c` → 应为 `27  value: 0.65`

### 限时抢购最终参数（可直接抄）
三钮全 `ButtonYellowBig`、rect 原生 `472×136`、`ButtonScale.normal = 0.65`
⇒ 视觉约 `307×88`，字号等比跟随；「不可用」态靠 `UIHelper.SetGray(go, true)`（恒真）。
