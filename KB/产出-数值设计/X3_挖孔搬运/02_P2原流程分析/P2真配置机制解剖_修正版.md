## 🔴 三条机制修正（与我们已实现的 X3 服务端骨架不一致，需裁决）

### ① 工具触发 ≠ 埋在格子里的工具格
**我们的实现**（dev_digkeys 骨架）：工具作为格子内容埋进 boardMap（`treasureId` 负值 -1/-2/-3），挖到即触发。
**P2 真机制**（`A_ARR_tool_trigger` 列）：按**挖掘次数窗口概率投放**——
```json
[{"dig_min":3,"dig_max":5,"trigger_count":1,
  "tool_pool":[{"tool_type":1,"weight":30},{"tool_type":2,"weight":30}]}]
```
= 「在本关第 3~5 次挖掘之间，触发 1 次工具，工具类型按权重从池里随机」。一关可配多个窗口。
⇒ 工具是**挖掘事件的附赠效果**，与"挖到哪一格"无关；玩家挖到第 N 下就会撞见，节奏由策划按窗口精确控制。
**影响**：服务端 `ActivityMeta.DigKeys.cs` 的工具逻辑要改（从"读格子内容"改成"按挖掘计数查窗口+权重随机"）；配置表 `ToolIDs` 列作废，换 tool_trigger 结构。**这是力总收尾时的头号改动项。**

### ② 奖励关（福利关）≠ 每 5 关固定
**P2 真机制**（`A_MAP_reward_window` 列 + 独立负数 level 行）：
```json
{"window_end_level":7,"reward_level_candidates":[{"reward_level_id":21830101,"weight":100}]}
```
= 「从本关到第 7 关这个窗口内，会插入一个奖励关，具体用哪个奖励关按权重从候选里选」。
奖励关**是独立配置行**：`level = -1 ~ -15`（负数编号！），id 21830101-21830115，固定 3×3 小棋盘，`treasure_pool` **带 weight**（主线的 pool 无 weight=全部必出；奖励关的 pool 有 weight=按权重随机选一个）。
⇒ 玩家侧观感=「不知道哪一关会撞到奖励关」，比固定第 5 关更有期待感。

### ③ 提示格数量 = `tip_num` 列（=用户说的"福利关高亮地块"）
分布实测：91 关 tip_num=0、14 关=1、13 关=2、1 关=4。对应客户端 `TipsPoints` → 格子 Special 态。
⇒ X3 关卡表**必须保留 tip_num 列**（我们已有 TipNum，语义确认无误）；高亮格生成=服务端摆放时从宝石占格中挑 tip_num 个。

## Level 编号约定（P2 用同一张表塞四类关卡，靠 level 值区分）
| level 值 | level_type | 数量 | 含义 | 特征 |
|---|---|---|---|---|
| 1 ~ 100 | 1 | 100 | **主线关** | 棋盘 3×3→8×8 渐进；cost 0→12；tip_num 0-4；49 关带 blocked_cells |
| **-1 ~ -15** | 2 | 15 | **奖励关/福利关** | 固定 3×3，cost 1→10，pool 带 weight 随机出 1 个宝物 |
| **9995 ~ 9998** | 3 | 4 | **特殊地形关**（实机整关换肤：沙黄背景+?文件夹插槽） | 固定 3×3，cost=10 |
| **9999** | 4 | 1 | **循环关**（100 关通关后无限循环） | 8×8，cost=0（消耗另有来源），tip_num=1 |
⇒ X3 侧 `Level` 列**必须允许负数与哨兵值**（导表 def 别加 `Level>0` 校验）；或改为「LevelKind 枚举 + Level 序号」两列更清晰（建议后者，避免负数魔法值）。

## 棋盘不是正方形（早前误判）
实测尺寸分布：3×3(22)/4×4(19)/**5×5(23)**/6×6(17)/7×7(8)/8×8(4) + **非方形 26 关**（3×4、3×5、4×5、4×6、**4×8**、5×6、5×7、6×7、6×8、7×5、7×6、8×6）。
⇒ 竖屏适配不能假设正方形棋盘：**最宽 8 列、最高 8 行**，横长棋盘（4×8）在竖屏下格子会被压小，交互设计要定"棋盘区最小格边长"和超出时的处理（缩放 or 滚动）。这条要进 demo 与交互稿。

## 宝物表 `event_hole_type.tsv`（46 种）
列=`id / variants(形状偏移 row,col 数组) / show / display_key(DK号 151105460+) / get_reward / unity_key / collection_group(1或2) / name / desc(LC key)`。
- `variants`=占格形状（相对左上角偏移），最大 3×3 九格。
- `collection_group` 只有 1/2 两组 → 对应图鉴两个页签（低阶/高阶）。
- `display_key` 数字号直接对应 P2 图素文件名 `NewDigkeyIcon\<号>.png`（40 张）。
- 名字是 `LC_ITEM_new_hole_digging_item_<英文名>_name`，英文名如 recon_drone(侦察无人机)/starmap_terminal(星图终端)——异星探索主题。

## 奖励结构（三列并存）
`reward`（过关奖励）/ `reward_s6`（S6 服差异化，X3 可不要但要知道存在）/ `free_reward`（免费奖励）。格式=`[{"typ":"item","id":111111000,"val":20}]`。`reward_show` 控制是否进奖励预览。
⇒ X3 现表只有单个 `RewardID`（指向 Reward 表组）——要么补 FreeRewardID 列，要么在 Reward 组内区分。

## X3 配置表补列建议（对我们 `ActvDigKeysLevel` 的缺口）
| 缺口 | 现状 | 建议 |
|---|---|---|
| 工具触发 | `ToolIDs` 竖线 id（机制错） | **换 `ToolTrigger` string 列**存 JSON（dig_min/dig_max/trigger_count/tool_pool 权重），或拆子表 `ActvDigKeysToolWindow` |
| 宝物池结构 | `TreasureIDs` 竖线 id | 需带 **num / allow_rotate / weight** → 换 JSON string 列或拆子表 |
| 不可挖格 | 无 | 补 `BlockedCells` string 列（JSON Row/Col） |
| 奖励关窗口 | 无 | 补 `RewardWindow` string 列（window_end_level + 候选权重） |
| 免费奖励 | 无 | 补 `FreeRewardID` |
| 关卡种类 | 靠 LevelType 数字 | 建议 `LevelKind` 语义枚举（主线/奖励/特殊地形/循环）替代负数与 9995+ 魔法值 |
| 奖励预览开关 | 无 | 补 `RewardShow` |
> ⚠️ 竖线分隔 string 列无法挂 tsv row3 跨表引用，JSON 列同理——依赖校验要在 def 里逐 id `register_depend_config_and_val`（见 [[reference_x3_new_actvtype_playbook]] 的 BD_ 前缀坑）。
